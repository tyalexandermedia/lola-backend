## TL;DR (read this first)

LOLA is **not** a greenfield and **not** an empty "AI OS." It is a working,
genuinely multi-client FastAPI system on Railway with a React operator app on
Vercel, real integrations (Google audit stack, GBP/GSC/GA4, GHL, Stripe,
CallRail, Resend, PostHog), and an existing owner dashboard at `/admin/hq`.

**The LOLA-OS brief's 9 phases are ~60% already built.** The real gaps are
narrow and nameable:

1. **No "what needs my attention today" layer.** `/admin/hq` is a raw metrics
   snapshot, not a prioritized brief. This is the single highest-ROI gap — and
   the data to fill it already exists in tables we already write to.
2. **No token/cost observability.** Every LLM call throws away the `usage`
   block the API already returns. Cheapest possible win.
3. **Client identity has two sources of truth** (a file registry *and* a DB
   table) kept in sync by hand. This must be reconciled before, not after, we
   build a cross-client brief on top of it.
4. **Persistence is conditional.** SQLite is durable only if `DB_PATH` points
   at a mounted Railway volume; the code silently falls back to an ephemeral
   file. Verify before trusting anything with memory.

Everything else the brief asks for (Client/Site model, Sandbar integration,
deterministic normalization, website factory) largely **exists** and should be
**preserved and reconciled**, not rebuilt.

## 2. What works (proven, in the live path)

- **The Growth Score audit pipeline** — PageSpeed + Places + Safe Browsing +
  Custom Search + on-page checks, concurrent, budget-capped (`AUDIT_API_BUDGET`),
  SQLite-cached. Runs at ~$0 (all free-tier). This is the top-of-funnel engine.
- **`db/api_cache.py`** — SHA256-keyed cache with per-API TTLs (PageSpeed 24h,
  Places 7d, etc.). "Cache hits are free quota-wise." Well-built, does its job.
- **The multi-client reporting/dashboard spine** — `reporting_clients` +
  `/reporting/public/{slug}` + `ClientReport.tsx`. Real, slug-scoped, live for
  Sandbar.
- **`/admin/hq` aggregator** (`main.py:1847`) — read-only, gathers the whole
  funnel concurrently. Solid data source; it just doesn't *prioritize*.
- **Revenue Agent** (`agents/revenue_agent/main.py`) — **deterministic Python,
  no AI**. Syncs tracking → pipeline, opens follow-up actions for stale
  estimates. This is the correct pattern and the seed of the priority engine.
- **Safe-by-default automation** — every outbound path and integration no-ops
  cleanly when its env var is unset (`DECISIONS.md`, verified across
  `ghl.py`, `runner.py`, `reviews/`). This is a genuine strength; keep it.
- **Stripe webhook fails closed** (`main.py:3921`, constant-time HMAC).
- **Website factory** — the Astro template + Randy Golden pilot deploy fast and
  independently. Preserve.

## 4. What is broken / at risk

1. **DB persistence is conditional (highest-severity infra risk).** Durable
   only if `DB_PATH` points at a mounted Railway volume; otherwise the code
   **silently falls back to ephemeral `./lola.db`** and loses everything on
   redeploy. `.env.example` doesn't define `DB_PATH`; no volume manifest ships
   in-repo. **Verify this in Railway before building anything that stores
   memory or history.** (`db/database.py:10-23`)
2. **`automation/wix_crm.py` has an undefined-variable bug** — param named
   `olaudit` but the body references undefined `audit`. Dormant, but broken if
   ever called. (`wix_crm.py:16-17,27`)
3. **In-process AI-visibility cache** (`main.py:3748` `_AI_VIS_CACHE`) — plain
   `dict`, unbounded, no TTL, lost on restart, wrong under multiple workers.
4. **Dual client source-of-truth drift** — file registry vs `reporting_clients`
   table can silently disagree (§3). A correctness hazard for any cross-client
   feature.

## 8. Where AI is used unnecessarily

**8 LLM call sites total** (all raw `httpx` to provider REST, no SDK, all
safe-by-default when keys unset). Most are legitimate — they generate
natural-language copy (lead packs, report emails, ad hooks) or simulate what a
third-party answer engine would say (the moat). Those are genuinely generative
and **should stay AI**.

**The one clear anti-pattern:**
- **`swarm/orchestrator.py` asks the model to invent numeric SEO scores**
  (`page_seo`, `tech_seo`, … out of 100) instead of computing them from the
  PageSpeed/Places data the audit pipeline already produces and caches. This is
  exactly "AI doing math a deterministic pipeline should do."
  (`swarm/orchestrator.py:80-88`)

**Done right (keep as the model):** the tracker classifies AI output with
**rule-based string matching** (`_score_recommendation_text` / `_name_matches`,
`case_studies/tracker.py:190`), not a second AI call. That's the deterministic-
first pattern working correctly — replicate it, don't undo it.

**Cost/token tracking is absent.** Every call parses only `data["content"]` and
**discards the `usage` block** the API returns. The only "cost" artifact is a
hardcoded string `"$0.08-$0.12"` (`swarm/orchestrator.py:184`). 6 of 8 LLM
sites have **no caching** (only cold-email variants ride `api_cache`, 30d).
There is no spend guardrail on LLM calls.

## 11. Recommended smallest Phase 1 (then STOP)

**Two thin, non-overlapping slices, both read-only or additive, no refactor, no
new dependency, no AI spend:**

### Slice 1 — Deterministic Priority Brief (the centerpiece)
A single read-only endpoint `GET /admin/brief` that:
- iterates active clients from **one** source (the `reporting_clients` table),
- reads **already-stored** signals — stale sent estimates
  (`revenue_agent_actions`), hot leads (`lead_scores`), GSC rank movement
  (`gsc_snapshots` / `case_study_rankings`), aging opportunities
  (`revenue_opportunities`),
- scores each candidate deterministically (`Impact×Urgency×Confidence÷Effort`),
  marks missing data **explicitly unavailable** (never invents a metric),
- returns the ranked top items as the `{title, business, reason, evidence[],
  recommended_action, urgency, effort, confidence, source}` shape the brief
  specifies.

Rendered as a **"3 things that need your attention"** block at the **top of the
existing `/admin/hq`**, reusing the Tailwind tokens and the `AdminRevenue`
action-item component pattern. **No AI in v1** — a later, optional pass can ask
the model to *phrase* the "why" after candidates already exist.

**Prerequisite folded in:** pick the `reporting_clients` DB table as the single
client source of truth so the brief iterates one list (the essential half of
Phase 2). Verifying `DB_PATH`→volume (**D**) is a 5-minute check that should
happen first.

### Slice 2 (optional, even smaller) — Token observability
Capture the `usage` block already returned by every Anthropic call, write it to
one `llm_usage` table, show a spend tile on `/admin/hq`. Independent of Slice 1;
ship first if you want the fastest possible win.

**Why this and not more:** it delivers the brief's *Definition of Success*
("open one dashboard, know what needs my attention") using data LOLA already
collects, touches no money path, adds no dependency, spends no tokens, and is
independently reversible. Everything past it (memory loop, auto-refresh
generalization, knowledge tree) waits for a real need — per the brief's own
"do not jump ahead" and Ty's standing "complete next best ROI" cadence.
